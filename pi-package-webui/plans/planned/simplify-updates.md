## Goal and acceptance

- Provide separate Pi and WebUI update actions. Remove the combined action and its automatic optional-companion updates.
- Run fixed commands through background PowerShell on Windows or Bash on Linux. A desktop terminal is not required. Show bounded, sanitized output/status and a small loading indicator in WebUI, without invented percentage progress.
- The Pi action runs `pi update` against the verified PATH installation only. The Pi-managed WebUI command also uses that PATH Pi. Do not silently substitute bundled or explicitly selected Pi, or change the runtime used by tabs.
- The WebUI action updates proven npm-global WebUI with `npm -g update @firstpick/pi-package-webui` and proven Pi user-managed WebUI with `pi update --extension npm:@firstpick/pi-package-webui --no-approve`, using its configured npm source when applicable. Update both eligible installations sequentially; project installations stay manual.
- Preview the exact executable, affected installations, commands, working directory, agent directory, and npm prefix where relevant. Bind execution to that confirmation rather than letting shell startup select different commands or settings. Distinguish active runtime versions from separate PATH or on-disk installations.
- Keep durable job identity, per-command completion evidence, and exclusion against overlapping updates across browser reconnects and server restarts. Distinguish launch, completion, verified success, and restart readiness. Unknown status blocks retry/restart until safe recovery.
- Require affected known work to be idle before mutation and prevent new affected work from racing update/restart. After all commands finish, automatically restart/reload only successfully changed, healthy active components once idle. Preserve sessions; do not restart unchanged or unowned external processes.
- If one WebUI installation fails, attempt the other when still safely identifiable. Report partial success and retain it after reconnect. A verified healthy active success may restart despite another installation's failure; failed or unverified active installations must not auto-restart.
- Support known npm WebUI sources only. Preserve settings, custom agent directories, ranges, and exact pins. Report skipped, unsupported, or unproven installations honestly and deduplicate actual affected roots. Do not deliberately include unrelated top-level packages; native dependency changes remain possible.
- Honor normal package-manager lifecycle-script behavior and existing user configuration, with a visible warning before execution. Do not automatically elevate permissions.
- Preserve localhost-only mutation authorization; remote clients must not launch shell commands. Do not run actual updates during tests.
- Retire exact-target staging, managed activation, and routine update rollback claims without breaking shared startup/tab-restoration helpers. Automatically migrate legacy pointers only to a validated, compatible equal-or-newer installed WebUI; retain pointer backups and old runtimes. Failed validation, incompatibility, or a downgrade retains the legacy launch path with manual guidance. No destructive cleanup.

## Classification and evidence

Complex feature. It changes user-visible update behavior across `bin/pi-webui.mjs` (update routes, owner detection, execution, activation), `bin/pi-webui-launcher.mjs` and `index.ts` (different entry points), `public/app.js` (update UI), update modules, tests, and README/TECHNICAL/DEVELOPMENT documentation. Shell launch and installing over running code introduce security and reliability risk. The preliminary complex classification stands; no contrary evidence was found.

## Review findings and interview resolutions

The existing findings remain acceptance obligations; the interview resolves their product decisions below.

### F1, high priority: bind the command to the intended Pi installation

`lib/update/resolver.mjs` selects an explicit `--pi` executable first, otherwise bundled Pi before PATH Pi. `bin/pi-webui.mjs` uses that identity for both tabs and update-version reporting. A bare `pi update` in a new shell can update a different installation while the WebUI continues to use and report the old one.

Resolved decision: both Pi commands use verified PATH Pi only. Resolve its exact invocation and affected root before confirmation; execute that invocation with the confirmed context. Keep active bundled/explicit runtime selection unchanged and report those versions separately. Do not restart unchanged active Pi merely because PATH Pi updated. Missing, incompatible, or unproven PATH Pi receives manual guidance; never fall back silently.

### F2, high priority: define the detached update lifetime

The current updater holds an install lock through execution and transfers ownership to the activation process when needed, in `lib/update/journal.mjs` and `bin/pi-webui.mjs`. A desktop terminal can outlive the HTTP request or its launcher process. Launch success therefore proves neither command completion nor that it is safe to retry or restart.

Resolved decision: background jobs have durable identity, completion receipts, and exclusion across reconnects/restarts. Show a small spinner until completion, or an explicit unknown/recovery state when evidence is lost. Parent exit is not completion. Run eligible WebUI installations sequentially; keep later command drivers viable, recheck identity, and attempt the other independent target after a failure when safe. Once all commands finish, auto-restart only verified successful changed active components when idle. Keep partial failure visible. Do not automatically release exclusion based only on server exit or elapsed time. Process identity and safe interrupted-job reconciliation must be specified and tested before accepting implementation.

### F3, medium priority: define Pi-managed scope and pinned-source behavior

The installed Pi package manager's `update(source)` matches package identity across both user and trusted project settings. One targeted command can therefore affect more than one installation. Its update path also skips exact-version npm pins and local sources, so a successful command exit does not necessarily mean WebUI changed.

Resolved decision: support Pi user scope only, with verified project exclusion and the configured agent directory. Automatic WebUI sources are npm-only. Preview every affected root; preserve ranges/pins; deduplicate physical installation effects rather than declarations. Exact pins, project copies, Git/local sources, links, and unsupported ownership receive skipped/manual status, not an update-success claim. Refuse automatic execution if user scope or target identity cannot be isolated safely. Verify actual installed results independently of the CLI's success message.

### F4, medium priority: assign shared consumers outside the update directory

The original worker boundaries omitted `index.ts`, `lib/component-update-state.mjs`, `lib/update-commands.mjs`, and update-related `package.json` scripts. These are existing consumers or contracts of the updater. In particular, `index.ts` imports `createRestoreFile` from `lib/update/supervisor.mjs` for ordinary WebUI restarts, and package checks reference the update supervisor executable.

Worker A owns these update-related changes as specified below. Preserve or relocate shared startup and tab-restoration helpers before removing obsolete supervisor code. Do not delete the update directory merely because managed activation is retired. Any additional shared-file changes require an explicit ownership assignment by the integration owner.
